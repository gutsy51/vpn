# Аварийный профиль для белых списков

Схема пилота: **Android -> доступный вход -> VPS-выход -> интернет**. Прямые профили AdminVPS и второго VPS остаются у клиентов. Входом может стать VPS или другой узел, где можно разместить свой TCP-сервис и до которого реально доходит трафик с нужной SIM во время ограничений. При полном отключении мобильных данных найдите работающий Wi-Fi или другой канал связи.

## 1. Проверить площадку перед переносом VPN

1. На кандидатном входе разместите простую HTTPS-страницу по своему имени, с действительным сертификатом и статическим телом. Лучше иметь маленький ответ и ещё один размером 64-128 КБ, чтобы выявить обрыв после начала передачи. Используйте уникальный параметр запроса или `Cache-Control: no-store` для теста.
2. Зафиксируйте результат в обычной LTE-сети. Во время ограничений выключите Wi-Fi и текущий VPN. Откройте известный доступный сервис оператора, контрольную страницу кандидата и дополнительный тестовый URL. Запишите время, город, SIM, результаты DNS, HTTPS и полной загрузки. Для сравнения повторите из Wi-Fi.
3. Сверьте результат с журналом своего входа. Если до адреса не доходит трафик, попробуйте другой вход или другую доступную сеть. Менять порты и конфиг VPS-выхода на этом этапе не требуется. Если обычный HTTPS доходит, переходите к отдельному тесту VPN по тому же адресу и порту.

Критерий перехода - HTTPS-ответ получен с нужной SIM именно в режиме ограничений. Успешный ответ лишь подтверждает доступность HTTPS. [Список доступных сервисов Т2](https://tver.t2.ru/promo/whitelist) | [Измерения обрывов после начала передачи](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet)

## 2. Настроить пилот

1. На сервере **выхода** выпустите отдельный VLESS-профиль для входного узла. Для уже работающего REALITY/Vision: адрес выхода, порт, UUID, SNI, клиентский ключ REALITY и short ID. Проверьте этот профиль с самого входа, прежде чем подключать телефон.
2. На выделенном **входе** разверните отдельный Xray по [инструкции Ubuntu](../deploy/README.md) и заведите отдельный VLESS-профиль телефона. Имя входа и параметры его REALITY берите именно от этого узла. Если тестовая страница на том же TCP/443, перенесите её TLS-обработчик на приватный порт. В качестве REALITY target задайте этот TLS-обработчик, а в `serverNames` - имя из его сертификата. При контейнерном Xray обработчик должен быть доступен в приватной Docker-сети, поскольку `127.0.0.1` внутри контейнера - сам контейнер. Публикуйте один внешний порт TCP/443 и проверьте обычный HTTPS повторно. [REALITY target](https://xtls.github.io/en/config/transports/reality.html)
3. На входе добавьте тег `mobile-ingress` к телефонному инбаунду и замените секции `outbounds` и `routing` в копии сгенерированной конфигурации фрагментом ниже. Замените адрес, UUID, SNI, клиентский ключ и short ID данными профиля **выхода**. Для ввода в 3x-ui применяется та же схема: исходящее соединение VLESS и правило по тегу входящего соединения. В standalone-пилоте держите фрагмент в локальном файле вне Git. При повторном запуске штатного генератора он будет перезаписан, поэтому сохраните изменённую копию и повторно примените её при обновлении.

~~~json
{
  "outbounds": [
    { "tag": "drop", "protocol": "blackhole" },
    {
      "tag": "vps-exit",
      "protocol": "vless",
      "settings": {
        "address": "exit.example.net",
        "port": 443,
        "id": "00000000-0000-4000-8000-000000000001",
        "encryption": "none",
        "flow": "xtls-rprx-vision"
      },
      "streamSettings": {
        "network": "raw",
        "security": "reality",
        "realitySettings": {
          "serverName": "exit-sni.example.net",
          "fingerprint": "chrome",
          "password": "<клиентский ключ REALITY выхода>",
          "shortId": "0123456789abcdef"
        }
      }
    }
  ],
  "routing": {
    "rules": [{ "type": "field", "inboundTag": ["mobile-ingress"], "outboundTag": "vps-exit" }]
  }
}
~~~

При таком порядке исходящих соединений трафик, для которого не нашлось правила, отправляется в `drop`. Это подходит для выделенного входа. Для общего сервера сохраните существующие правила остальных инбаундов. Если HTTPS-страница обслуживается соседним контейнером, в Compose дайте ему сетевой алиас вида `web.internal`, настройте TLS на `8443` и используйте `web.internal:8443` в `XRAY_REALITY_TARGET`. В `XRAY_REALITY_SNI` укажите публичное имя из сертификата, а не внутренний алиас. [VLESS outbound](https://xtls.github.io/en/config/outbounds/vless.html) | [Маршрутизация Xray](https://xtls.github.io/en/config/routing.html)

Перед переключением сохраните предыдущую конфигурацию. Для standalone-конфигурации проверьте файл и затем пересоздайте контейнер, чтобы он примонтировал изменённую версию:

~~~bash
sudo docker compose --env-file /dev/null run --rm --no-deps xray \
  run -test -c /etc/personal-vpn/xray.json
sudo docker compose --env-file /dev/null up -d --force-recreate
~~~

## 3. Проверить на телефоне

1. Импортируйте в v2RayTun отдельный профиль входа, например `Мобильный резерв`.
2. С выключенным Wi-Fi подключитесь и проверьте внешний IPv4 через два HTTPS-ресурса. Он должен быть адресом выхода. Проверьте загрузку полной страницы, сайт с доменным именем и повторное подключение после перехода Wi-Fi -> LTE.
3. Повторите по этой SIM во время ограничений. Зафиксируйте результат по этапам: обычный HTTPS, подключение к входу, получение данных и ожидаемый IP выхода. Проверьте также, что прямые профили остались работоспособны из обычной сети.

| Результат | Что проверять |
| --- | --- |
| HTTPS к входу недоступен | Доступность адреса, имени и сертификата с этой SIM. Проверить режим ограничения |
| HTTPS доступен, VLESS не поднимается | SNI, ключ, UUID, short ID и журнал Xray входа в момент попытки |
| VLESS поднимается, данных нет | Отдельно проверить маршрут вход -> выход и HTTPS через него |
| IP выхода совпадает и HTTPS стабилен | Сохранить профиль как аварийный и перепроверить при следующем ограничении |

Критерий готовности - передача данных через ожидаемый выход на конкретной SIM в реальном режиме ограничений. Доступность может меняться между операторами, регионами и периодами.
