# План развития VPN Manager

Цель переписывания - управлять VPN на нескольких VPS через Telegram, MAX и одну консоль. Этот документ описывает план первой версии. Предыдущая реализация сохранена в [архиве](../archive/README.md). Очерёдность работ задана в [плане коммитов](roadmap.md).

## Размещение и доступ

Один менеджер постоянно работает на VPS. Он обслуживает обоих ботов, запускает проверки, записывает события и доставляет алерты. В первой версии ноутбук и телефон служат клиентами. Закрытие меню или отключение ноутбука не прерывает мониторинг.

| Способ доступа | Как будет работать |
|---|---|
| Telegram и MAX | В каждом боте доступны кнопки "Узлы", "Инциденты" и "Состояние менеджера". Из алерта можно перейти к карточке узла. |
| Терминал | Команда `ssh -t user@host vpn-manager` открывает меню на VPS из Windows CMD, PowerShell, WSL или Termux. Для этого на клиенте нужен SSH и доступ к учётной записи на VPS. |
| Скрипт | Например, `ssh user@host vpn-manager status` возвращает сводку и код завершения. Скрипт и меню вызывают одни и те же операции. |
| Обслуживание | Из CLI можно проверить конфигурацию, запустить и остановить менеджер, прочитать его журнал. Команда `vpn-manager serve` запускает все фоновые задачи вместе. |

Основной вариант установки на Ubuntu VPS - служба systemd. Для AdminVPS с 1 ГБ ОЗУ и одним CPU сначала измерим потребление памяти вместе с работающим VPN. Docker Compose рассматриваем как дополнительный способ поставки с теми же настройками и командами. Доступ к журналам должен работать через меню независимо от способа установки. Windows и WSL также остаются целевыми средами запуска менеджера.

## Что можно сделать с узлом

Операция всегда адресована конкретному узлу и сервису. Например, `vpn-manager logs vpn-main xray` означает журнал Xray на узле `vpn-main`. Один и тот же сервис может работать на нескольких VPS.

| Задача | Ожидаемый результат |
|---|---|
| Открыть карточку | Видны сервисы, результаты проверок, время и точка наблюдения. Устаревшие данные и ненастроенные проверки явно подписаны. |
| Проверить сейчас | Администратор запускает одну или все настроенные проверки узла. Команда начинает свежую пробу или присоединяется к уже выполняющейся пробе той же цели. Карточка показывает последнее сохранённое наблюдение с временем измерения. Разовая диагностика не сбрасывает счётчик плановых отказов. |
| Открыть журнал | Администратор выбирает узел и сервис. Менеджер читает последние записи из systemd или Compose локально либо по SSH. Журнал самого менеджера доступен через CLI и после остановки службы. |
| Разобрать инцидент | Несколько последовательных неудач открывают инцидент. При восстановлении приходит сообщение с длительностью сбоя. История доступна и при потере SSH-соединения с узлом. |
| Управлять сервисом | Администратор выбирает узел, сервис и действие: запуск, остановку, перезапуск или поддерживаемую сервисом команду. После выполнения видны ожидаемое и фактическое состояния. |
| Выпустить inbound или клиента | Администратор может создать входящее подключение (inbound) на выбранном узле, добавить клиента в существующий inbound или выполнить оба шага последовательно. |
| Управлять приложениями | Отдельный раздел CLI "Приложения" показывает менеджер, Telegram, MAX, установленные VPN-клиенты и сайт. Для каждого доступны состояние, журнал и поддерживаемые действия. |

Проверяем по отдельности TCP-порт, HTTPS-ответ панели, состояние процесса и прохождение трафика через VPN-клиент. Последняя проверка нужна для случая, когда Xray запущен и порт открыт, но трафик через туннель не проходит.

Для Telegram роли задают TELEGRAM_ADMIN_IDS и TELEGRAM_USER_IDS, для MAX - MAX_ADMIN_IDS и MAX_USER_IDS. Значения содержат ID отправителей через запятую. Пользователь видит карточки, результаты и историю инцидентов. Администратор также запускает проверки, читает журналы и управляет узлами в личном чате. При совпадении ID в двух списках действует роль администратора. Отправитель вне обоих списков не получает сведений об инфраструктуре. Получателя алертов задаём отдельно через TELEGRAM_CHAT_ID или MAX_CHAT_ID.

## Как устроить первую версию

- Инвентарь узлов ведём вручную в .env. Для подключения указываем адрес, порт, пользователя и имя переменной с паролем. Пароли VPS и панелей храним в локальном .env. Поддержку ключей и SSH-алиасов добавим отдельным этапом.
- CLI, Telegram и MAX вызывают общие операции. Модуль каждой платформы отвечает за ввод, кнопки и представление результата. Адаптеры SSH, systemd и Compose отвечают за исполнение.
- Планировщик ведёт состояние проверок. SQLite хранит результаты, инциденты, историю действий и очередь доставки. Переход состояния и постановка алерта в очередь выполняются в одной транзакции. Ошибка доставки в один канал не блокирует другой.
- Один активный менеджер владеет командами и рассылкой. При полном отказе его VPS он сам не сможет оповестить о сбое. Для обнаружения такого отказа потребуется независимый наблюдатель.

Первый сквозной сценарий для приёмки: на тестовом VPS порт остаётся открытым, а трафик через VPN перестаёт проходить. При выключенном ноутбуке пользователь получает алерт, открывает карточку, читает журнал, подтверждает перезапуск и видит результат новой проверки туннеля. Сценарий проверяем в обоих ботах.

Разбиение кода, этапы реализации и критерии приёмки описаны в [плане разработки](development.md).
