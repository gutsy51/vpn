# Порядок переписывания

Каждый пронумерованный этап предусматривает отдельный коммит с законченным результатом. Порядок первых четырёх этапов фиксирован. Для следующих этапов границы уточняем по результатам стенда.

| Коммит | Результат | Проверка готовности |
|---|---|---|
| 1. Подготовить репозиторий и документы | Предыдущие исходники, тесты, зависимости и инструкции собраны в archive/. В корне остаются документы новой версии. | Из README доступны карта функций, план разработки и архив. Локальные секреты и состояние исключены из Git. |
| 2. Реализовать CLI менеджера | Одна точка входа, меню и команды config check, список узлов, карточка, свежая проверка и журнал. Первый пример - Linux VPS на AdminVPS с systemd и x-ui. Пароль берётся из переменной окружения. | В Windows CMD и Ubuntu один сценарий проходит через CLI с тестовым SSH. Добавление второго Linux-узла требует только записи в .env. |
| 3. Реализовать Telegram | Получение команд, карточка узла, проверка и журналы через общие операции. Здесь появляется serve как единая точка запуска фоновых компонентов. | Тестовые обновления проверяют обе роли, отказ неизвестному отправителю и получение журнала администратором в личном чате. |
| 4. Реализовать MAX | Команды и кнопки MAX дают доступ к тем же операциям. Два бота работают под одним менеджером. | Те же сценарии выполняются на событиях MAX. Отключение одного канала не мешает второму. |
| 5. Добавить мониторинг и алерты | Расписание, история в SQLite, инциденты, очередь доставки и восстановление после перезапуска. | На стенде порт открыт, но трафик через туннель не проходит. После восстановления доставляется отдельное уведомление. |
| 6. Добавить управление сервисами и раздел приложений | Запуск, остановка, перезапуск и проверка результата. CLI показывает менеджер, ботов и настроенные приложения. | Подтверждение привязано к исполнителю и цели. При потере связи результат сверяется до повторного действия. |
| 7. Реализовать выпуск VPN-доступа | Через панель 3x-ui создать клиента в существующем inbound, затем поддержать создание inbound. | Выданный профиль проходит сквозную проверку. Повтор запроса после обрыва не создаёт второго клиента. |
| 8. Подготовить эксплуатацию | Установка службы на Ubuntu, измерение ресурсов на малом VPS, публичный сайт и дополнительный вариант поставки Compose. | Перезагрузка восстанавливает работу. Проверены сайт, VPN и журналы. После приёмки перенесённых сценариев отдельным коммитом удаляем archive/. |
 
## Граница Linux и провайдера

Инвентарь описывает адрес, порт SSH, пользователя, имя переменной пароля и сервисы узла. Модуль SSH отвечает за соединение, тайм-аут и результат команды. Модуль systemd знает, как прочитать состояние и журнал указанного юнита. Первому CLI достаточно этих двух модулей. Название AdminVPS используется как метка в инвентаре.

Проверка панели 3x-ui и выпуск клиента относятся к интеграции с VPN-панелью. Заказы, баланс, тикеты и включение машины через кабинет относятся к API хостинга. Такой адаптер добавляем при появлении конкретной задачи. Состояние хостинга и SSH-доступность гостевой ОС могут различаться.

Код новой версии размещаем в src/, тесты - в tests/. Архив служит источником примеров и граничных случаев. При создании pyproject.toml явно ограничиваем сборку и поиск тестов этими рабочими каталогами. До удаления архива сверяем пользовательские сценарии, включая те, которые решили вывести из проекта. Репликация менеджеров остаётся отдельным этапом после первой версии.
