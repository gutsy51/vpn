# План разработки

## Границы модулей

| Модуль         | За что отвечает                                                                                                                                                                                                                                                        |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| inventory            | Читает каталог узлов, сервисов, inbound и проверок из .env. Разрешает ссылки на настройки подключения.                                                                                                    |
| monitoring           | Выполняет пробы, записывает наблюдения, открывает и закрывает инциденты. Ручная проверка возвращает результат с временем и точкой наблюдения.              |
| services             | Запрашивает состояние и журнал сервиса, выполняет поддерживаемые действия локально или по SSH.                                                                                                        |
| provisioning         | Создаёт inbound и клиентов. Первую реализацию проверяем на тестовой панели 3x-ui.                                                                                                                                          |
| runtime              | Управляет жизненным циклом менеджера, ботов и планировщика. Даёт CLI состояние компонентов.                                                                                                              |
| console и messaging | Разбирают команды и кнопки, передают в сценарий исполнителя и цель, показывают результат. Каждая платформа извлекает ID отправителя из своего события. |
| storage              | Хранит наблюдения, инциденты, очередь доставки и историю операций в SQLite.                                                                                                                                                |

Новую реализацию начинаем с CLI по [плану коммитов](roadmap.md). Выделяем модуль, когда появляется первый сквозной сценарий для него. Для действия важны узел, сервис, исполнитель и ожидаемый результат. Проверку прав выполняет общий сценарий при исполнении, в том числе при повторном нажатии старой кнопки.

## Интерфейсы

В ботах путь управления начинается с карточки узла. Кнопки "Сервисы", "Журналы" и "VPN-доступ" доступны администратору. Перед изменением бот показывает имя VPS, цель и действие. Подтверждение действует для одной операции и одного отправителя. В CLI те же действия доступны из меню и напрямую для скриптов.

Раздел CLI "Приложения" нужен для сопровождения самой установки. У менеджера есть запуск, остановка и журнал даже при остановленном процессе. У каждого бота есть состояние соединения, журнал и возможность переподключения без перезапуска второго бота. У VPN-клиента доступны запуск, остановка, состояние туннеля и сквозная проба. У сайта - состояние веб-сервиса, журнал и HTTP-проверка. Оба раздела CLI вызывают один сценарий, если показывают один и тот же сервис.

## Очередность работ и приёмка

1. **Инвентарь и доступ.** Описать один стендовый VPS, панель и сервис. Команда `config check` находит повтор имени, неизвестную цель, неверный порт и отсутствующую переменную окружения до сетевого подключения. Шаблон .env.example содержит имена параметров без значений секретов. SSH-клиент менеджера должен уметь подключаться по паролю без интерактивного ввода и проверять ключ хоста. Пользователь может войти в CLI по SSH с обычным запросом пароля.
2. **Карточка и свежая проверка.** Провести одну проверку через CLI, Telegram и MAX. На стенде остановить сервис сразу после успешной пробы. Карточка показывает старый результат с его временем, а команда проверки обнаруживает новое состояние. Одновременные запросы одной и той же цели используют выполняющуюся пробу.
3. **Журналы, алерты и управление.** Сначала реализовать состояние, журнал, запуск, остановку и перезапуск одного systemd-сервиса, затем добавить Compose. Отдельно обозначить управление автозапуском, если его поддерживает способ установки. Дополнительную команду, например проверку конфигурации или reload, показывать только для подходящих сервисов. После остановки проверить, что процесс остановился. После запуска VPN проверить прохождение трафика. При обрыве SSH после отправки команды сверить состояние, обозначить неизвестный исход и сохранить его в истории.
4. **Выпуск VPN-доступа.** Сначала добавить клиента в существующий inbound. Затем добавить создание inbound с выбором протокола, адреса и порта и проверкой конфликта. Передать профиль подключения администратору в личном чате или локальном CLI. В истории сохранить имя узла, идентификаторы объектов и результат. Если inbound создан, а клиент не выпущен, показать завершённый шаг и продолжить с клиента. При тайм-ауте сверить состояние панели перед повтором. Приёмка завершается подключением тестового клиента и сквозной пробой.
5. **Приложения.** Собрать операции в разделе CLI "Приложения". Проверить восстановление менеджера после остановки, диагностику одного отключённого бота и чтение журнала при недоступности приложения.
6. **Публичный сайт по IP.** Отдельная задача - разместить обычную публичную страницу, которая открывается при обращении к IP VPS. Цель владельца - чтобы по адресу сервера был доступен сайт. Уменьшение вероятности распознавания VPN остаётся предположением. На стенде согласовать порты, поведение HTTP и HTTPS и сосуществование сайта с рабочими VPN-подключениями. Приёмка - страница открывается извне, а проверка VPN продолжает проходить. Идею направлять на сайт дополнительный трафик оставить открытой до определения его источника и назначения.
7. **Несколько менеджеров.** После первой версии перейти к [плану репликации](replication.md). Для будущего обмена уже в первой версии сохранять идентификатор события, источник и время наблюдения.

## Как проверять изменения

Каждую задачу берём вертикальным срезом: одно пользовательское действие, его реализация и проверка результата через штатную точку входа. В описании задачи указываем ожидаемое поведение при успехе, отказе и повторе. Пароли, токены и клиентские профили исключаем из журналов и истории синхронизации.

| Уровень       | Что проверяем                                                                                                                                                                                                                                                                                                  |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Сценарий     | Роли обеих платформ, пустые списки, неизвестного пользователя, конфликт ролей, чужое или повторное подтверждение. Для просмотра проверяем отсутствие управляющего вызова. |
| Адаптер       | Аргументы SSH, ответы панели, тайм-аут после принятого запроса, остановку и проверку состояния. Используем подмену транспорта.                                                                                      |
| Интеграция | SQLite во временном каталоге, конкурирующие проверки, перезапуск менеджера, недоступность одного канала и доставку очереди после восстановления.                                                    |
| Приёмка       | CLI из Windows CMD и Ubuntu, бот на тестовом контуре, тестовый VPS с 3x-ui. Проверяем действие и результат глазами пользователя.                                                                                                             |

Штатные команды: `uv sync --locked`, `uv run pytest`, `uv run ruff check src tests`, `uv run ruff format --check src tests`, `uv run pyright`. Первую библиотеку для парольного SSH и конкретные методы 3x-ui выбираем при работе с тестовой версией панели.
